# PRD: v1.1.0 — Reliability & Polish

## Executive Summary

Four focused improvements that transform VPN Audit Suite from a functional prototype into a reliable, readable tool. The changes fix real bugs (cache miss, event-loop blocking), eliminate a single point of failure (external IP API), surface a new class of leaks (split-tunnel bandwidth), and replace raw JSON output with human-readable structured results.

## Problem Statement

VPN Audit Suite v1.0.0 has four categories of issues that erode user trust and limit utility:

1. **Fragile external IP detection** — The sole API dependency (ip-api.com) has no fallback, and the REST endpoint (`GET /api/external-ip`) instantiates a new `ExternalIPChecker` per request, bypassing the 30-second TTL cache entirely.

2. **Raw JSON results** — Audit results render as `JSON.stringify` blobs. Users must mentally parse nested objects to understand what leaked, which protocols were detected, and whether the kill switch held.

3. **Aggregate-only bandwidth** — `psutil.net_io_counters()` returns system-wide totals, hiding split-tunneling leaks where traffic flows through the physical adapter instead of the VPN tunnel.

4. **Event-loop blocking** — Synchronous Scapy `sniff()` calls (up to 30s for fingerprinting, 30s for killswitch) and `time.sleep(0.5)` in bandwidth estimation block the async event loop, freezing the live dashboard during audits.

## User Stories

### US-1: Reliable external IP detection
**As a** VPN user
**I want** external IP lookups to succeed even when one API is unavailable
**So that** I can always verify my VPN masking status

**Acceptance Criteria:**
- External IP lookup tries at least 2 fallback APIs when the primary fails
- The REST endpoint `/api/external-ip` uses a shared singleton so the 30s cache works
- The WebSocket monitor continues using its existing `ExternalIPChecker` instance (no regression)
- API source is indicated in the response (`source` field)
- All fallback logic is covered by unit tests with mocked HTTP calls

### US-2: Structured audit results
**As a** VPN user
**I want** audit results displayed as readable tables with severity indicators
**So that** I can immediately understand what leaked and how serious it is

**Acceptance Criteria:**
- **Leak Detection** renders as a 3-row table (DNS / WebRTC / IPv6) with pass/fail/warning badges per check, and expands to show leaked servers/IPs when failed
- **Traffic Fingerprinting** renders a protocol breakdown (WireGuard / OpenVPN / HTTPS / Other) with packet counts and a visual bar, plus the VPN ratio and verdict
- **Kill Switch** renders a summary showing duration, leaked vs. tunnel packet counts, per-interface breakdown, and time-to-block when applicable
- **Full Audit** retains its sub-result summary and updates individual cards
- Raw JSON is no longer shown to users (developers can still view via API docs or browser devtools)
- Existing CSS variables (`--color-pass`, `--color-fail`, `--color-warning`) are reused for badges

### US-3: Per-interface bandwidth visibility
**As a** VPN user
**I want** to see bandwidth usage per network interface
**So that** I can detect if traffic is leaking through my physical adapter instead of the VPN tunnel

**Acceptance Criteria:**
- Dashboard shows per-interface bandwidth (Mbps) in the Network Interfaces section
- Non-tunnel interfaces with significant traffic (>0.1 Mbps) are visually flagged
- The aggregate bandwidth gauge continues working (uses sum of all interfaces)
- WebSocket `bandwidth_mbps` field is backward-compatible (still a number), with per-interface detail in a new `bandwidth_per_interface` field

### US-4: Responsive dashboard during audits
**As a** VPN user
**I want** the live dashboard to remain responsive while audits are running
**So that** I can monitor my connection status during the exact moments it matters most

**Acceptance Criteria:**
- Running any audit (leaks, fingerprint, killswitch, full) does not freeze the WebSocket monitor
- Latency, bandwidth, and external IP continue updating during audits
- No changes to the audit API response format (backward-compatible)
- Existing tests continue to pass without modification (mocks are at module boundary)

## Requirements

### Functional Requirements

#### F1: External IP Fallback + Cache Fix

**F1.1 — Fallback API chain**
- Add an ordered list of API sources in `external_ip.py`:
  1. `http://ip-api.com/json/?fields=query,country,city,isp,org,as` (current, free, no key)
  2. `https://ipinfo.io/json` (free tier, 50k/month, HTTPS)
  3. `https://ifconfig.me/all.json` (free, HTTPS, minimal fields)
- On failure (network error, timeout, non-200, JSON decode error), try the next source
- Normalize response fields to a common schema: `{ip, country, city, isp, org, vpn_masked, source, status, timestamp}`
- Add a `source` field indicating which API provided the result (e.g., `"ip-api.com"`)

**F1.2 — Singleton cache fix**
- Promote `ExternalIPChecker` to a module-level singleton in `routes.py`
- The `GET /api/external-ip` endpoint uses this shared instance
- The `ConnectionMonitor` in `websocket.py` continues using its own instance (both benefit from caching independently)
- Cache TTL remains 30 seconds

**F1.3 — Error resilience**
- If all APIs fail, return the last cached result (if any) with `status: "cached"` instead of `status: "error"`
- Only return `status: "error"` when all APIs fail AND no cached result exists

#### F2: Structured Result Rendering

**F2.1 — Leak Detection rendering**
- Three-row table: DNS, WebRTC, IPv6
- Each row shows: check name, status badge (PASS/FAIL/WARNING), detail summary
- DNS detail: "No leaks" or "Leaked to: 8.8.8.8, 1.1.1.1"
- WebRTC detail: "No public IPs exposed" or "Exposed: 203.0.113.5"
- IPv6 detail: "No IPv6 leaks" or "Leaked: 2001:db8::1 on eth0"

**F2.2 — Traffic Fingerprinting rendering**
- Protocol breakdown table: Protocol | Packets | Percentage
- Horizontal bar proportional to packet count (using CSS width%)
- VPN ratio displayed with color coding (green <3%, yellow 3-10%, red >10%)
- Verdict text from the `reason` field
- Packet statistics (mean size, timing) shown in a secondary detail row

**F2.3 — Kill Switch rendering**
- Summary row: Duration, Total Packets, Tunnel Packets, Leaked Packets
- If leaked > 0: per-interface breakdown table (Interface | Leaked Packets) and time-to-block value
- If leaked = 0: green "Kill switch held — no leaks detected" message

**F2.4 — Consistent styling**
- Status badges use existing CSS vars: `--color-pass` (#4caf50), `--color-fail` (#f44336), `--color-warning` (#ff9800)
- Result tables use compact styling consistent with the route/interface lists
- All rendering functions are module-internal to `app.js` (no new files)

#### F3: Per-Interface Bandwidth

**F3.1 — Backend changes**
- Change `psutil.net_io_counters()` to `psutil.net_io_counters(pernic=True)` in `estimate_bandwidth()`
- Compute per-interface deltas over the sample interval
- Return both aggregate `bandwidth_mbps` (sum) and `bandwidth_per_interface` dict:
  ```json
  {
    "bandwidth_mbps": 12.5,
    "bandwidth_per_interface": {
      "eth0": 11.2,
      "tun0": 1.3,
      "lo": 0.0
    }
  }
  ```
- Filter out interfaces with 0.0 Mbps from the per-interface dict to reduce noise

**F3.2 — Frontend changes**
- In the Network Interfaces section, append a small bandwidth indicator to each interface item
- Non-tunnel interfaces with >0.1 Mbps traffic get a warning highlight
- Tunnel interface traffic shown in green (expected)
- Aggregate bandwidth gauge continues using the `bandwidth_mbps` field

#### F4: Async Execution Fixes

**F4.1 — Audit route handlers**
- Wrap synchronous audit calls in `asyncio.get_event_loop().run_in_executor(None, ...)`:
  - `LeakDetector().run()` (5s DNS sniff)
  - `TrafficFingerprinter().run()` (30s sniff)
  - `KillSwitchTester().run()` (30s sniff)
- The `/api/audit/full` endpoint runs all three sequentially in the executor (not parallel, to avoid Scapy conflicts)

**F4.2 — Monitor bandwidth**
- Replace `time.sleep(0.5)` in `estimate_bandwidth()` with an async-compatible approach
- Option A: Make `estimate_bandwidth()` async and use `asyncio.sleep(0.5)` — requires `snapshot()` to become async
- Option B: Run `estimate_bandwidth()` in an executor from `snapshot()` — minimal API change
- Prefer Option B to minimize changes to the `snapshot()` / `stream()` interface

**F4.3 — Monitor subprocess calls**
- Replace `subprocess.run()` in `measure_latency()` and `get_routing_table()` with `asyncio.create_subprocess_exec()` if called from async context
- Or wrap in executor if keeping synchronous signatures (simpler, lower risk)
- Prefer executor wrapping: `get_routing_table()` and `measure_latency()` stay synchronous, called via `run_in_executor` from `snapshot()`

### Non-Functional Requirements

- **Backward compatibility:** All existing API response schemas remain valid; new fields are additive only
- **Cross-platform:** All changes work on Windows, Linux, and macOS
- **Performance:** Dashboard should never freeze for more than 100ms during audits
- **Testing:** All new logic covered by unit tests using existing mock patterns (Scapy, psutil, urllib mocked)
- **No new dependencies:** All features implemented with stdlib + existing deps

## Success Criteria

1. `GET /api/external-ip` returns valid data when ip-api.com is unreachable (fallback works)
2. Calling `GET /api/external-ip` twice within 30s hits cache (verified by mock call count)
3. All three audit cards render structured tables instead of raw JSON
4. Running a 30s fingerprint audit does not freeze the WebSocket monitor
5. Per-interface bandwidth is visible in the dashboard, with non-tunnel traffic flagged
6. `python -m pytest tests/ -v` passes with no regressions
7. No new npm/pip dependencies introduced

## Constraints & Assumptions

- All fallback APIs are free-tier and require no API keys
- ipinfo.io free tier allows 50,000 requests/month (sufficient for local tool)
- ifconfig.me returns minimal fields (ip only in some modes); may need `/all.json` endpoint
- Scapy `sniff()` is not thread-safe — concurrent sniff calls from multiple audit endpoints must be avoided (sequential execution in full audit)
- `psutil.net_io_counters(pernic=True)` is available on all platforms (verified in psutil docs)
